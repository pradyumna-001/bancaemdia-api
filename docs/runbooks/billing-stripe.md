# Stripe billing operations

Status: implementation under validation; production NO_GO. Never use real charges or real card/customer data in tests. Test contract fixtures do not prove Stripe account approval.

## Configuration and test setup
- Apply migrations with the administrative role; run API/workers with the ordinary non-owner application role. No secrets in commands, Git, issues or logs. Inject STRIPE_SECRET_KEY and STRIPE_WEBHOOK_SECRET via the secret store; the adapter rejects live keys and live objects.
- BILLING_ENABLED defaults false. BILLING_CURRENCIES is the verified presentation-currency allowlist (initial BRL only). BILLING_RETURN_URL must point at the deployed authenticated subscription screen. STRIPE_PORTAL_CONFIGURATION must be a test portal configuration: cancellation enabled at period end, plan changes disabled. STRIPE_TEST_AUTOMATIC_TAX defaults false: the Brazilian sandbox rejected Tax settings because the account country is unsupported. This test-only setting does not waive tax obligations. A reviewed tax solution for the seller's establishment and destination markets is a production gate (ADR 025).
- Use API version 2024-06-20 for outgoing requests and the webhook endpoint. The adapter deliberately pins the documented subscription current_period/invoice.charge shape. A version upgrade requires new contract fixtures and sandbox replay, not a dashboard-only switch.
- Disable Adaptive Pricing in the test account's Checkout settings and verify the charged currency matches the catalog. The pinned API does not expose the newer adaptive_pricing parameter, so disabling it is an account configuration gate, not an enforced request flag. Checkout explicitly supplies the catalog currency; do not enable currency conversion or alternate currency options without a separately validated pricing policy.
- Create the product and recurring test Prices administratively, using explicitly designated test fixture amounts. Insert draft catalog rows, verify Price currency/unit_amount/interval against the account, then publish the test row. Never copy test amounts to the production catalog. Commercial prices remain undecided.
- In a disposable test database, activate billing using `SELECT billing_activate_rollout()`. Before card confirmation a user is AWAITING_CARD/READ_ONLY. Complete hosted test Checkout with Stripe's official sandbox inputs, without storing card details. Assert the card-confirmed trial bounds differ by precisely 604800 seconds and no money is collected during that interval. Persist only sanitized assertions and event IDs hashed in evidence.
- Run Celery worker consuming materialization and Celery beat. `billing.reconcile` runs every minute and discovers up to 100 least-recently-reconciled mapped accounts. Ensure this rate meets the user count/SLO before launch; scale scan cadence/batch with measured backlog.

## Delivery and recovery
The webhook authenticates the original bytes with a five-minute timestamp tolerance and accepts test events only. A minimal inbox row is committed before acknowledgement; duplicates use a primary-key no-op. No raw event, email, card, hosted URL or provider error body is stored. Polling the database avoids the commit/enqueue gap. Every delivery retrieves current remote state under the same subscription lock; receipt timestamp/order never determines access.

Delivery failures receive bounded exponential backoff, eight attempts, then `dead`. An unresolved event older than three days also enters dead letter. Query aggregate counts by state/attempts and oldest received timestamp; alert on dead > 0, old pending, or stale reconciliation. A provider outage never extends local paid bounds. Existing entitlement ends at its persisted boundary.

The worker exports aggregate Prometheus series `billing_inbox_events{state}`, `billing_oldest_pending_seconds`, `billing_oldest_scan_seconds`, `billing_reconciliations_total{outcome}` and `billing_scan_timestamp_seconds` through the existing worker metrics endpoint/multiprocess registry. The SECURITY DEFINER health query returns counts and ages only. Heartbeat means the scan completed, not that every provider call succeeded; inspect the failure counter too. Install `infra/observability/billing.rules.yml` with billing enabled, scope selectors to the deployment and wire the approved operator receiver. Five-minute freshness is the initial alert threshold; measure backlog before scaling. Validate alerts with a test provider outage, dead notification and stopped beat in staging. Merely committing these rules does not deploy monitoring or notify an operator.

Recovery: repair configuration/provider outage, inspect only sanitized codes, then an operator may reset selected dead event IDs to pending with attempts=0 and next_attempt_at=now(). Do not delete the dedup identity. Re-run the worker; current Stripe state wins. Periodic reconciliation also repairs a completely missed notification. For an ambiguous checkout with no saved session after 23h, do not create another operation: inspect the customer's subscriptions and Stripe request log using the saved operation metadata, bind the confirmed session/subscription administratively, or prove no remote creation before retiring the reservation. Stripe idempotency retention is not an indefinite dedup guarantee.

## State and cancellation
Card confirmation starts one trial. The first grant requires no pending SetupIntent plus a completed test Checkout belonging to the mapped customer and subscription; an attached card alone does not establish confirmation. Trial access remains until its exact immutable end even after cancellation. A paid period requires an active subscription and paid current invoice/charge, matching catalog Price and no full refund/dispute. Failed, incomplete, paused or unpaid subscriptions do not establish a paid period. Partial refund retains access; full refund or dispute revokes the current paid period. Reconciliation of an older refund checks the current invoice so it cannot revoke an unrelated newly paid period. A checkout redirect only displays the current server state.

Cancel renewal via POST /api/v1/billing/cancel or the verified portal. Cancellation at period end preserves the remainder; no immediate proration/refund is initiated. Refunds are an operator workflow in Stripe, never an automatic real-money operation by this code. Account deletion requires confirmed cancellation so it cannot leave an orphan subscription.

## Write enforcement and export
`require_write_access` covers authenticated mutating routes; collection checks after its token establishes the user. Extraction checks before AI cost and materialization checks again. Database triggers check fresh database time on each owned business mutation, covering direct SQL, workers, replays and queued retries. HTTP denial is 402 with detail=account_read_only; clients retain pending data and direct the user to subscription management. Login, GET/read/analytics, billing, cancellation and JSON/XLSX export remain accessible. The paid flag is never usuarios.ativo.

Future owned business tables must install `billing_write_guard` before their writes are enabled; regression tests compare schema and installed triggers. Telegram/titulares PRs are still on the older chain; their billing compatibility must be validated after integration. Bot transport acknowledgements/outbound explanations are control records, while drafts/materialization are protected writes. Do not ACK materialized or discard an extension outbox on 402.

Concrete pending integrations: PR #134 must protect holder/account history tables; #139–141 must check access before draft creation/edit, photo download/AI and confirmation, and again inside queued materialization. The #138 inbox must enqueue an explanatory reply on denial while acknowledging transport only. Account link/revoke and delivery of the denial are control operations. These implementations are absent from main; the API guards here do not constitute evidence that those branches are protected.
