# AWS environments

This project defines separate staging and production Terraform roots over shared modules. It has **not** provisioned an AWS account. The defaults create a large, continuously billed footprint: two NAT gateways, a Multi-AZ RDS primary plus an in-region read replica and a cross-region read replica, six Redis nodes, an ALB, and (after deployment is enabled) fifteen Fargate tasks per environment. Review the plan and budget before enabling an apply.

The owner's AWS spending targets are about R$ 100/month initially, up to R$ 200/month for the first 100 users, and up to US$ 300/month at 1,000 users. The current stack exceeds them even with `deploy_enabled=false`; see the [budget reconciliation and open request to the administrator](../../docs/decisions/aws-initial-budget.md). Keep `TF_APPLY_ENABLED` unset and do not apply either environment until the architecture and budget agree.

## Architecture and deliberate differences from #41

- The main VPC has two public ALB subnets and two private ECS/RDS/Redis subnets across two AZs, each private subnet routed through a NAT gateway in its AZ. A separate private VPC in `dr_region` hosts the cross-region RDS read replica. The API uses the **in-region** replica for `/ready` and dashboard reads; the DR replica is for recovery, not the live read path.
- RDS PostgreSQL 16 is `db.r6g.large`, Multi-AZ, 200 GiB gp3, 35-day automated backup, encryption, deletion protection, and an AWS-managed master password. The same-region and cross-region replicas are separate DB instances.
- Application cache and rate limits use `cache.r6g.large` Redis Cluster with two shards and one replica per shard. Celery retains a separate one-shard Redis group for its broker and result backend, which require ordinary Redis URLs and databases 0 and 1. Both groups have automatic failover and encryption at rest and in transit. See [AWS cluster-mode client requirements](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/BestPractices.Clients.Redis.Discovery.html) and [Celery Redis broker configuration](https://docs.celeryq.dev/en/latest/getting-started/backends-and-brokers/redis.html).
- The S3 backend configures both its lockfile and the bootstrap DynamoDB lock table, as requested by #41. [Terraform supports both during migration](https://developer.hashicorp.com/terraform/language/backend/s3#state-locking), although DynamoDB locking is deprecated; the pinned Terraform version must be checked before future upgrades. Grant the OIDC roles `DescribeTable`, `GetItem`, `PutItem`, and `DeleteItem` on the lock table.
- `deploy_enabled=false` provisions foundations without launching ECS tasks. Secrets Manager holds secret *metadata* only; Terraform never puts application secret values into state. Once the application DB role, eight secret values, migrations, and immutable image digest are ready, set `deploy_enabled=true`. The ECS task execution role can read only those eight secret ARNs. The application task role can read and write only `media/*` in the private uploads bucket, for signed review photos. When enabled, Terraform also creates an API canary service at desired count zero and a second target group. The CD workflow owns ECS task revisions and HTTPS listener weights after provisioning.
- The existing WAF module is attached to the ALB. API and worker tasks include an ADOT collector sidecar that scrapes Prometheus metrics and exports them, along with application OTLP traces, to CloudWatch. The PromQL alerting module is enabled with `notification`. Basic ALB/RDS alarms, ECS logs, JSON error metric filters, and an operations dashboard are included. Confirm CloudWatch ingestion and alarm queries in each live environment; subscribe an operator endpoint to the default SNS topic before relying on basic notifications.
- RDS preloads `pg_cron` for the dashboard's 15-second refresh. After the parameter group is active, the migration owner runs `python -m bancaemdia.cli.configure_painel_cron` on the primary. Measure refresh duration and replica lag with representative data before claiming the under-30-second target.
- New review photos are copied to `media/<sha256>` in the private uploads bucket and receive a five-minute signed GET URL. Existing database photos remain available through the authenticated local route. Run `python -m bancaemdia.cli.backfill_midia_s3` with a maintenance database credential and `S3_UPLOAD_BUCKET` to migrate historical photos; it keeps the database bytes as a fallback.
- Celery Beat has a dedicated Fargate service, and schedules the Telegram transport tick every five seconds. Prefork workers write Prometheus files to their own task-local `/tmp/prometheus` directory and expose port 9100 to the collector sidecar.

## Bootstrap and first deployment

1. Choose primary/DR AWS Regions, a Route 53 hosted zone, and separate `staging-api`/`api` names. Ensure account quotas and cost budget cover the resources. Obtain an ACM-valid public domain under the hosted zone.
2. With an approved AWS identity, initialize and apply `bootstrap/` once in the primary Region. Protect its initial local state, then migrate it to the new S3 backend. The bootstrap bucket has versioning, encryption and public access blocking. Use the printed bucket name in each environment's `backend.hcl` (copy its `.example` file) and a different state key per environment. Do not commit `backend.hcl`, `terraform.tfvars`, plan files, or state.
3. Copy `environments/staging/terraform.tfvars.example` to a local `terraform.tfvars`; set real Region, DR Region, API domain, and Route 53 zone. Run `terraform -chdir=infra/terraform/environments/staging init -backend-config=backend.hcl`, `plan`, and review the full resource and cost changes. Apply only after approval. `deploy_enabled=false` means this first apply does not yet expose a working API.
4. Create a dedicated application DB role on the RDS primary, grant only the permissions required by the existing schema/RLS policies, and apply Alembic migrations. Use the RDS-managed master secret only for privileged setup/migrations, never as the ECS application credential. Populate the eight `bancaemdia/staging/*` secrets through the approved secret pipeline: `database-primary-url`, `database-replica-url`, `jwt-secret-key`, `coleta-token-secret`, `anthropic-api-key`, `upload-webhook-secret`, `telegram-bot-token`, and `telegram-webhook-secret`. Both DB URLs must use `postgresql+asyncpg://` and TLS (`ssl=require`), with the same application role but the primary and in-region replica endpoints respectively. Never place URL values in Terraform variables or CI logs.
5. Push the tested Docker image to the provisioned ECR repository. Set `image_uri` to its immutable `repository@sha256:<digest>` reference, set `deploy_enabled=true`, and review a new plan before applying. Confirm ECS has two healthy API targets, `/ready` succeeds, private workers consume both queues, WAF is attached, ALB access logs arrive in S3, RDS backups and replica lag are healthy, and SNS delivery is tested. Then configure the [CD workflow](../../docs/runbooks/cd.md); migrations remain a separately reviewed operation.
6. Repeat with `environments/production/` only after the production GitHub environment has an approval rule, production secrets exist, and staging has passed the full k6 profile. Production uses a separate state key and separate resources.

## CI inputs

`.github/workflows/terraform.yml` runs `fmt`, `validate`, and mocked architecture tests on PRs. A same-repository PR runs a real staging plan and comments a **resource-action summary** when `TF_STAGING_ROLE_ARN` and `TF_STATE_BUCKET` repository variables exist. The full plan stays in the Actions run and is not uploaded because plan files can contain sensitive state. Fork PRs only validate. GitHub OIDC roles require scoped AWS trust policies, including repository and branch/environment conditions; no long-lived AWS access key is used.

Set repository variables `TF_REGION`, `TF_DR_REGION`, `TF_STATE_BUCKET`, `TF_ROUTE53_ZONE_ID`, `TF_STAGING_API_DOMAIN`, `TF_PRODUCTION_API_DOMAIN`, `TF_STAGING_ROLE_ARN`, and `TF_PRODUCTION_ROLE_ARN`. Optional deployment variables are `TF_STAGING_IMAGE_URI`, `TF_PRODUCTION_IMAGE_URI`, `TF_STAGING_DEPLOY_ENABLED`, and `TF_PRODUCTION_DEPLOY_ENABLED`. `TF_APPLY_ENABLED=true` arms automatic staging apply on a merge to `main` and production apply on a release tag reachable from `main`. Keep it unset until the first plans and credentials have been reviewed. Protect the GitHub `production` environment with required reviewers before arming production apply.

`terraform validate` proves provider schema compatibility, not AWS quotas, live plan feasibility, secret contents, migration state, or `/ready`. The first real plan and apply must use the target AWS account.
